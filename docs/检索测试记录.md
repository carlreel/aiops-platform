# 检索质量测试记录

> 测试日期：2026-10-20
> 环境：WSL2 Ubuntu 24.04 + Docker 29.9.1 + pgvector(pg16) + Ollama(qwen2.5:3b / bge-m3)
> 语料：3 篇运维文档（磁盘巡检、显存告警、离线交付），共 3 个切片（chunk_size=512, overlap=64, top_k=5）
> 说明：语料规模仅用于功能验证，不代表生产检索效果；生产需 100+ 文档与 30-50 条评测集。

---

## 一、测试方法

三类问题覆盖 RAG 的三种典型场景：

| 类型 | 目的 | 判据 |
|---|---|---|
| 事实型 | 能否准确召回并复述原文数字 | 答案中的数值与原文一致 |
| **边界型** | 资料中没有时，能否**拒绝回答**而非编造 | 必须明确表达"无法回答" |
| 流程型 | 能否把单个切片组织成有序步骤 | 步骤完整、顺序正确、带引用 |

调用方式：`POST /query {"question": "..."}`

---

## 二、测试结果

### 用例 1｜事实型

**问题**：磁盘使用率达到多少需要清理？

**答案**：
> [1] 磁盘使用率超过 80% 时，需要清理 Docker 镜像与日志文件；若清理后仍超过 90%，应申请扩容。因此，磁盘使用率达到 90% 需要清理。

**召回**：

| rank | doc_id | score | 命中内容 |
|---|---|---|---|
| 1 | ops-01 | 0.0328 | 磁盘使用率超过 80% 需清理，超过 90% 申请扩容 |
| 2 | ops-02 | 0.0161 | 显存超 90% 触发 P2 告警 |
| 3 | ops-03 | 0.0159 | 离线交付流程 |

**判定**：✅ 检索正确（目标文档 rank 1，score 为 rank 2 的 2.04 倍）

**❗ 发现的问题**：回答末句「磁盘使用率达到 **90%** 需要清理」**与原文矛盾**。
原文是「超过 80% 需清理」「超过 90% 申请扩容」，模型把两个阈值串了。
- 归因：`qwen2.5:3b` 参数小，多阈值数值推理能力弱
- 影响：**检索没错，生成错了**——这是 RAG 系统中典型的「召回正确但生成失真」
- 处置：生产环境应换 7B 以上模型，或在 prompt 中强制「逐条摘录原文，禁止自行归纳数字」

---

### 用例 2｜边界型（★ 最关键）

**问题**：公司今年的营收是多少？

**答案**：
> 根据现有资料无法回答。

**判定**：✅ **正确拒答**

**意义**：这是判断 RAG 是「真系统」还是「套壳调 API」的分水岭。
套壳实现会把问题直接丢给大模型，模型会顺着编一个数字；
本系统在生成层强制「无召回则拒答」，因此能守住边界。

---

### 用例 3｜流程型

**问题**：离线交付的完整流程是什么？

**答案**：
> 离线交付的完整流程是：在有网机器上执行 docker save 导出镜像与模型，拷贝到内网机器后执行 docker load，再运行 docker compose up -d 启动服务。[1]

**召回**：ops-03（rank 1）、ops-02、ops-01

**判定**：✅ 步骤完整、顺序正确、带 `[1]` 引用标记

| 批次 | 类别 | 篇数 |
|---|---|---|
| batch1-linux | Linux 系统运维 | 8 |
| batch2-docker | Docker 与容器 | 6 |
| batch3-monitor | 监控与告警 | 5 |
| batch4-security | 安全加固与等保 | 5 |

**当前规模**：33 篇文档 / **113 个切片**（chunk_size=512, overlap=64, top_k=5）

**入库性能**：30 篇批量入库耗时 **8 秒**（含 bge-m3 向量化，平均每篇 0.27 秒）。
这个速度说明 bge-m3 的批量 embed 效率很高，100 篇级别的知识库入库在 30 秒内可完成。

### 观察与结论

1. **跨文档召回准确**：用例 4 同时召回了 `docker-06`（日志轮转）、`linux-01`（磁盘排查）、`linux-05`（日志体系），三篇从不同角度覆盖同一问题，这正是知识库应有的效果。
2. **专业问题命中率高**：用例 6、7 涉及本项目的特有经验（WSL2 网络、显存降级），检索仍能精确定位，说明语料中的具体技术细节被有效向量化了。
3. **拒答稳定**：扩语料后拒答能力没有退化，说明拒答机制基于召回阈值而非语料规模。
4. **引用存在重复 doc_id**：同一文档的不同切片可能同时被召回（如用例 4 的 `linux-05`、`docker-06` 各出现两次）。这不是错误，RRF 融合按切片排名，但**展示层应做去重或标注切片位置**，否则看起来像召回不够精确。
5. **延后发现**：用例 5 的 rank1 与 rank2 分数接近（0.0164 / 0.0161）且来自同一文档，说明同一文档相邻切片间存在语义重叠，可考虑在 RRF 之后加一步「同文档去重」，只保留该文档的最高分切片。
