# 部署手册

> 项目：aiops-platform｜私有化 AI 知识库运维平台
> 版本：v1.0｜适用环境：单机 Linux / WSL2（Ubuntu 22.04+）

---

## 一、环境要求

| 项 | 最低 | 说明 |
|---|---|---|
| CPU | 4 核 | 内存瓶颈比 CPU 更常见 |
| 内存 | 12 GB | Ollama 约 6 GB + 容器栈约 4 GB |
| 磁盘 | 40 GB 可用 | 镜像约 8 GB，模型约 4 GB |
| 显卡 | 8 GB 显存 | 跑 4B 量化模型；无独显可改 CPU 推理（慢 5-10 倍） |
| 系统 | Ubuntu 22.04/24.04 或 WSL2 | 需 Docker 24+ 与 Compose v2 |
| 网络 | 首次部署需外网 | 之后可完全离线运行 |

## 三、部署前检查

```bash
# 1. Docker 与 Compose 版本
docker --version && docker compose version        # 需 >= 24.0 / v2

# 2. 端口占用（8000/9090/3000/5432 不能被占用）
ss -tlnp | grep -E ':(8000|9090|3000|5432)'

# 3. 内存与磁盘
free -h && df -h /

# 4. Ollama 是否可用
curl -s http://localhost:11434/api/tags
```

## 四、部署步骤

### 4.1 准备 Ollama（宿主机）

```bash
# 必须监听所有网卡，否则容器连不上
# Windows：系统环境变量 OLLAMA_HOST=0.0.0.0:11434，然后重启 Ollama 服务
# Linux：systemctl edit ollama → Environment="OLLAMA_HOST=0.0.0.0:11434"

ollama pull qwen3:4b     # 约 2.6 GB
ollama pull bge-m3       # 约 1.2 GB
```

**连通性验证（必做）**

```bash
docker run --rm --add-host=host.docker.internal:host-gateway curlimages/curl:latest \
  -s http://host.docker.internal:11434/api/tags | head -c 200
```

> 若失败：在 WSL 内执行 `ip route show default | awk '{print $3}'` 取宿主机 IP，
> 写入 `.env` 的 `OLLAMA_BASE_URL=http://<该IP>:11434`。

### 4.2 拉取代码与配置

```bash
git clone <仓库地址> aiops-platform && cd aiops-platform
cp .env.example .env
vi .env          # 至少改 POSTGRES_PASSWORD 与 GF_PASSWORD
```

### 4.3 启动

```bash
docker compose pull        # 拉基础镜像
docker compose build       # 构建 rag-api
docker compose up -d
docker compose ps          # 全部 Up / healthy 才算成功
```

### 4.4 验证清单

| # | 检查 | 命令 | 期望 |
|---|---|---|---|
| 1 | 容器健康 | `docker compose ps` | 6 个服务均 Up (healthy) |
| 2 | 依赖健康 | `curl -s localhost:8000/health` | `"db":"up","ollama":"up"` |
| 3 | 入库 | `curl -X POST localhost:8000/ingest ...` | 返回 `chunks > 0` |
| 4 | 问答 | `curl -X POST localhost:8000/query ...` | 有 `answer` 且 `sources` 非空 |
| 5 | 指标 | `curl -s localhost:8000/metrics \| head` | 出现 `rag_query_total` |
| 6 | 监控 | 打开 `localhost:9090/targets` | 4 个 target 全 UP |
| 7 | 看板 | 打开 `localhost:3000` | 能登录、导入 1860 |
| 8 | 巡检 | `make health` | 异常 0 项 |

## 五、常见问题对照表

| 现象 | 可能原因 | 排查与处置 |
|---|---|---|
| `rag-api` 启动就退出 | 数据库未就绪 | 服务已内置 30 次重试；仍失败则 `docker logs aiops-rag-api` 看 DSN |
| `/health` 中 `ollama: down` | 宿主机未监听 0.0.0.0 / 防火墙拦截 | 见 4.1 连通性验证；Windows 防火墙放行 11434 |
| 首次查询很慢（>20s） | 模型冷启动，需加载进显存 | 正常现象，预热一次后恢复到 2-5s |
| 查询报 `dimension mismatch` | 换了 embedding 模型导致维度变化 | 维度必须与 `db/init.sql` 中 `vector(1024)` 一致；换模型需重建表 |
| `pgvector` 起不来 | 旧数据卷残留 | `docker compose down` 后确认 `data/pg` 已删再起（会丢数据，先备份） |
| 建索引很慢 | HNSW 建索引消耗大 | 先入库再建索引；数据量小时可改 `ivfflat` |
| 中文检索召回差 | 关键词路未生效 | 确认已 `CREATE EXTENSION pg_trgm`，并检查 `simplicity` 阈值 0.02 |
| 磁盘涨得快 | 容器日志无限制 | 在 compose 加 `logging.options.max-size: 10m` |

## 六、回滚方案

```bash
# 1. 保留现场
docker compose logs > logs_$(date +%F_%H%M).log
bash scripts/backup.sh

# 2. 回滚到上一版本
git log --oneline -5
git checkout <上一个稳定 tag>
docker compose up -d --build

# 3. 数据回滚（仅在数据损坏时）
gunzip -c backup/ragdb_<时间戳>.sql | docker exec -i aiops-pgvector psql -U rag -d ragdb
```

**回滚判定**：任一核心接口 30 分钟内无法恢复，或数据校验不一致 → 执行回滚并上报。

## 七、交接说明

接手人需要知道的 5 件事：

1. 所有配置在 `.env`，**不要改 compose 里的硬编码**。
2. 数据在 `./data/`，删掉即清空，先备份。
3. 模型跑在宿主机 Ollama，容器故障不影响模型。
4. 巡检入口：`make health`，输出里 `[FAIL]` 即异常。
5. 告警规则在 `prometheus/alerts.yml`，改完 `docker compose restart prometheus`。
